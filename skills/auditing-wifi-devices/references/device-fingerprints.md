## 一、识别判据优先级

设备类型判定按下列顺序取**首个命中的高置信判据**，不要凭 MAC 前缀猜具体型号。

| 优先级 | 判据 | 置信 | 说明 |
|---|---|---|---|
| 1 | SSDP/UPnP 自报的设备类型（NT 字段） | 高 | 设备自己声明，可信度高于其他判据 |
| 2 | SSDP 的 SERVER 字段（含型号串） | 文本佐证 | 常带设备型号，写进报告的判据栏供交叉印证；脚本不据它单独定类型 |
| 3 | 端口指纹（专有端口） | 中高 | 见 [§三 端口指纹表](#端口指纹主动全端口扫描)；对**随机 MAC 尤其有用**——OUI 走不通时它是主要的主动判据 |
| — | mDNS 服务实例名 | 辅助 | **不参与自动判定**，脚本只作佐证列出；能拿到可读名称，但不一定能对应到 IP |
| 4 | MAC 的 OUI 厂商 | 中 | 只到厂商级，整机型号不可见；随机 MAC 查不到 |
| 5 | 未知（含随机 MAC） | 低 | 列入待确认，转 §五 取主机名 |

**写入报告时必须带判据来源**：同一台设备同时有 SSDP 与 OUI 时，取 SSDP 并注明「SSDP 自报」，置信度高。

### 判据的时效性：快照，不是事实

**所有判据只对「这一次采集」有效，不得跨快照继承。** 两种常见误判：

- **IP 会换主人**：同一个 IP 在一周内可以先后属于手机和笔记本。上一轮把 `.109` 判成「iOS 设备」，这一轮同一 IP 已换成安卓机——若沿用上轮结论就是错的。**跨快照只按 MAC 认人。**
- **ARP 表里有 MAC ≠ 有实体**：路由器的「IP与MAC绑定 / 静态地址分配」会给已离网设备保留静态 ARP 条目并**代答** ARP 请求，于是该 IP 永远能解析出 MAC、永远进「在线清单」。本机私有地址轮换后，自己的旧条目也会这样残留。

⚠️ **别用「ICMP 全丢 + 端口全超时」去分辨幽灵**：休眠中的手机与幽灵条目在网络侧完全同构，按这条判据会成批误标正常设备。要分清两个方向：

- **有 RST ⇒ 主机一定在线**（任一端口回 `ECONNREFUSED`/`ECONNRESET` 即可，见 §三 errno 三档）——这条正向判据可靠，可以用。
- **全超时 ⇒ 只能说「这次没回」**，推不出「不存在」——这条负向判据不可用。

所以幽灵判定拿不到网络侧证据，只能靠外部信息，两条都写进报告让用户拍板：

1. 到路由器「IP与MAC绑定 / 静态分配」页核对，看该 IP-MAC 对是不是管理员手工绑的；
2. 比对**本机历史 MAC**：若可疑条目的 MAC 与本机以前的私有地址相同，就是本机残留，直接剔除。

## 三、服务自报指纹（SSDP / mDNS）

### SSDP 的 NT / ST 字段

> 设备主动通告用 `NT`，被 `M-SEARCH` 查询后的单播应答用 `ST`——**两者字段名不同、含义相同**，判定时取先有的那个（脚本已同时解析）。只解析 `NT` 会把「只回应查询」的那批设备整批丢掉。

| 字段值 | 设备类型 |
|---|---|
| `urn:schemas-upnp-org:device:InternetGatewayDevice:1` | 路由器 / 网关 |
| `urn:schemas-upnp-org:device:MediaRenderer:1` | 音箱、电视、投屏接收端 |
| `urn:schemas-upnp-org:device:MediaServer:1` | NAS / DLNA 媒体服务器 |
| `urn:schemas-upnp-org:device:Printer:1` 或含 `printer` / `ipp` | 打印机 |
| `urn:schemas-upnp-org:device:Basic:1` | 通用 UPnP 设备（多为 IoT） |

SSDP 的 `SERVER` 字段常直接带型号，例如 `vxWorks/5.5 UPnP/1.0 <型号>/1.0`——这类字符串会写进报告的判据栏供交叉印证，但**不单独定类型**：定类型仍按 `NT`/`ST`、端口指纹或 OUI。

### mDNS 服务类型

| 服务类型 | 设备类型 |
|---|---|
| `_airplay._tcp` / `_raop._tcp` | AirPlay 接收端（Apple 设备、音箱、电视） |
| `_companion-link._tcp` | Apple 设备 |
| `_ipp._tcp` / `_printer._tcp` | 打印机 |
| `_smb._tcp` | 开启文件共享的电脑 / NAS |
| `_hap._tcp` | HomeKit 配件 |
| `_googlecast._tcp` | Chromecast / Google 音箱 |
| `_mi-connect._udp` | 小米设备 |
| `_workstation._tcp` | Windows 工作站 |

脚本当前浏览 `_airplay` / `_raop` / `_companion-link` / `_http` / `_workstation` / `_ipp` 六类；上表其余类型需手工 `dns-sd -B` 补。

**mDNS 实例名默认只当佐证**，但**可以反查 IP**——多跑两条命令即可，值得做：能拿到「设备名 ↔ IP ↔ MAC」的绑定，比 OUI 靠猜强得多。

```bash
dns-sd -B _airplay._tcp local.                     # 1) 浏览，记下输出里的实例名
read -r INSTANCE && export INSTANCE                # 2) 粘贴实例名后回车（read 不求值，export 供下一步取用）
python3 -c 'import os,subprocess;subprocess.run(["dns-sd","-L",os.environ["INSTANCE"],"_airplay._tcp","local."])'
# 3) 上一步输出里有 host（形如 xxx.local.），再解析成 IPv4：
dns-sd -G v4 <host>.
```

示例（**已脱敏**，仅示意字段结构）：

```
某投屏器._airplay._tcp.local. can be reached at Android.local.:45329
   deviceid=d4:12:43:xx:xx:xx  model=AppleTV2,1  srcvers=<版本号>
```

`deviceid` 通常是该设备的 MAC，但不同固件不保证一致——采信前**必须**与 ARP 表里同一 IP 的 MAC 核对：对上才写「高置信」，对不上就不要拿它当 MAC 用。部分第三方投屏器/机顶盒为兼容 AirPlay 会沿用 `model=AppleTV2,1` 标识，**不要据此判成 Apple 设备**，以 `deviceid` 与厂商标识为准。

> 脚本只做第 1 步（浏览实例名），`-L/-G` 需按上面的命令手工跑；用户设备名属个人信息，写进报告时不脱敏就不要外传。**实例名来自设备自报，属外部数据**：先用 `read` 取值并 `export`（不经 shell 求值）、再经环境变量传给 Python（`os.environ["INSTANCE"]`，不经过 shell 解析），落进报告前须经脚本内的报告清洗处理；确需拼 shell 时用脚本提供的转义函数（基于 `shlex.quote`）。**禁止 `INSTANCE='<实例名>'` 这类单引号包裹**——自报名里的 `'` 会闭合引号进而注入命令。

### 端口指纹（主动全端口扫描）

脚本首轮只探**精选强特征端口**（二十来个，几秒完成，判定优先级见 §一），**不提供全端口扫描入口**（`--no-ports` 只能关）。当 SSDP 自报拿不到、OUI 也查不到（**随机 MAC 设备几乎必然如此**）、且精选端口未命中时，需要更深线索只能自己写脚本对**单台目标**做 1–65535 并发 `connect_ex` + banner 探测。

⚠️ 全端口扫描有侵入性：资源受限的 IoT 设备与老款摄像头可能因连接数激增而失联，与「只读审计」的定位冲突——先确认是自家设备、挑空闲时段、一次只扫一台，并在报告里注明做过这一步。

**判定用端口（与下表一一对应）**：

| 端口 | 含义 | 可判定为 | 置信 |
|---|---|---|---|
| **62078** | Apple **lockdownd**（设备同步/配对服务） | **iOS 设备（iPhone / iPad / iPod）**——macOS 不监听此口，可与 Apple OUI 设备区分 | 高 |
| 9100 | JetDirect 打印 | 打印机 | 高 |
| 554 | RTSP 流 | 网络摄像头 / 影音设备 | 高 |
| 1883 | MQTT | IoT 智能设备 | 高 |
| 32400 | Plex | 媒体服务器 | 高 |
| 8123 | Home Assistant | 家庭自动化主机 | 高 |
| 3689 | DAAP | Apple 音乐共享 | 高 |
| 7000 / 7100 | AirPlay | 投屏 / 音响设备 | 高 |
| 445 / 139 | SMB / NetBIOS | Windows 或文件共享设备 | 中 |
| 22 | SSH | Linux / 路由器 / 树莓派 | 中 |
| 3389 | RDP | Windows 远程桌面 | 中 |

**仅记录、不参与判定（`AUX_PORTS`）**：80、443、8080、8443、5000、5001、49152。其中 **49152** 是系统动态端口，常与 62078 同现作 iOS 佐证，但它本身不构成判据（很多设备都会开高位端口）。

> 全端口扫描不在脚本范围内，需要时自行写（见下）。

**响应行为也是判据**：
- **TCP 握手成功但任何写入立即 `Connection reset`** → 典型的「只接受已配对/白名单主机」，与 Apple lockdownd 行为一致；
- 握手成功但读超时无 banner → 客户端应用的监听 socket（私有协议），只能定到「带应用服务的智能设备」一级，不可再深挖；
- **`connect_ex` 的 errno 分三档**：`0` 开放；`ECONNREFUSED` / `ECONNRESET`（Darwin 61/54，Linux 111/104）＝对端回了 RST，**主机活着但端口关闭**——「零开放端口」的设备多半属于这一档，这本身就是活着的证据；`ETIMEDOUT` / `EAGAIN` ＝ 无任何应答，**只能说明「这次没回」，既不能证明在线也不能证明不在线**（设备睡着、防火墙丢包、幽灵条目都长这样）。

**交叉验证是必须的**：把同一批端口探到已知设备上（如基线里的 Apple / 手机 / IoT），确认某端口确实是**该设备族独有**，再下结论。避免把某台设备偶开的高位端口当成厂商特征。

**交叉验证示例**：一台随机 MAC 设备，OUI 与 SSDP/mDNS 全部落空，全端口扫描仅 62078 + 49152 开放、建连即 RST；把同批端口探到同网两台 Apple（macOS）设备上，均不监听 62078 ⇒ 判定为 iOS 设备，中高置信。

## 四、随机 MAC

**判定**：MAC 首字节的 U/L 位（0x02 位）为 1 即为本地管理地址，也就是操作系统启用的私有 Wi-Fi 地址（iOS / Android / Windows 默认开启）。

**表现**：厂商库查不到（接口返回 Not Found 属正常），无开放端口，多数不回应 ICMP。

**处理原则**：**不标记为可疑**——隐私特性导致的不可查是设计使然，报告须写明原因。

**定性路径**（按成本从低到高，与 SKILL.md 一致）：

1. **端口指纹**（网络侧就能做完，成本低）：OUI 永远查不到，但设备仍会开监听端口——脚本内置的精选强特征端口首轮即可给出判据（见 §三 端口指纹表），需要更深线索再做全端口扫描 + banner 探测。
2. 取 §五 的 DHCP 客户端列表**主机名**（权威度高于其他判据，但需登录路由器后台）；
3. 引导用户在设备上关闭该网络的「私有 Wi-Fi 地址」后重连。

⚠️ **白名单注意**：**固定 MAC 白名单对随机 MAC 设备天然失效**——设备每次重连/换网络都可能生成新地址，白名单里的旧条目将永远匹配不到，「长期离线」很可能只是「地址轮换了」。核对白名单时遇到随机 MAC 条目查无，**先判断是真离线还是已换地址**，不要直接断言设备丢失；要让白名单稳定，必须在设备端关闭该网络的私有地址。

**轮换的三连带影响**（同一台设备的私有地址反复更换时会同时出现）：

| 影响 | 现象 | 处理 |
|---|---|---|
| IP 抢位 | 每次换 MAC 都重新 DHCP，会拿走别台设备刚空出来的 IP | 报告按 MAC 认人；别按 IP 讲「同一台设备」 |
| 静态绑定失效 | 路由器「IP与MAC绑定」绑的旧 MAC 永久对不上，还会把旧 IP 变成代答幽灵 | 换完 MAC 需重新绑；或干脆绑定硬件 MAC |
| 定时断网 | 「家长控制 / 上网限时」白名单按 MAC 判，掉出名单后每到限制时段即断，白天恢复正常 | 关闭该网络的私有地址后把真实 MAC 加回白名单 |

**周期**：并非每次连接都换，而是按网络记忆 + 周期性更换（同一 SSID 通常按周计，约 1–3 周一个地址）。因此「偶发、按周计的 IP 变化」基本可归因于此，不必怀疑有人蹭网。

### 回填厂商名（参数化，勿拼 SQL）

WebFetch 查到的厂商名属**外部数据**，写回台账时用占位符与环境变量传值，禁止字符串内插。该公共接口有速率限制，**逐条间隔查询**，批量补齐优先走本地库：

```bash
DB='<台账.db>' VENDOR='<已清洗厂商>' MAC='<mac>' python3 -c 'import os,sqlite3;c=sqlite3.connect(os.environ["DB"]);c.execute("UPDATE devices SET vendor=? WHERE mac=?",(os.environ["VENDOR"],os.environ["MAC"]));c.commit()'
```

厂商名先经 `sanitize()` 清洗；`sqlite3` 的双引号内插字符串有注入风险，不用。

## 五、主机名获取路径

按优先级排列。主机名是定性随机 MAC 设备的**权威来源**。

| 路径 | 可行性 | 说明 |
|---|---|---|
| 路由器 DHCP 客户端列表 | ★ 首选 | 含主机名，且覆盖当前休眠的设备（只要租约未过期） |
| 设备端关闭私有地址后重连 | ★ 首选 | 真实 MAC 出现后可直接查厂商 |
| mDNS / Bonjour 自报 | 中 | 只覆盖会广播服务的设备 |
| NetBIOS 名称 | 中 | 主要覆盖 Windows |
| 路由器 DNS 反向解析（PTR） | 低 | 多数家用路由器不注册反向记录，常只返回 IP 反写 |
| 被动监听 DHCP 报文 | 低 | 需绑定 67/68 特权端口，普通权限下不可行 |

**实用手法**：设备只在 DHCP 注册时上报主机名。遇到主机名缺失或显示为未知时，让该设备**断开 Wi-Fi 再重连**（或重启设备）即可触发上报，随后刷新路由器列表。

**关键认知：开随机 MAC ≠ 拿不到主机名**。开着私有地址的随机 MAC 设备，照样可能在 DHCP 列表里上报主机名——**厂商私有命名规则与 MAC 随机化是两套独立机制**。因此 DHCP 列表始终是第一顺位，不要因为「MAC 是随机的」就跳过它直接下结论说无法定性；只有 DHCP 里显示「匿名主机」的（多为 iOS 与部分 IoT，不主动上报主机名）才需退到端口指纹、关闭私有地址或物理核对。

## 六、常见家用路由器后台入口

用于与扫描结果交叉核对（路径名因固件版本略有差异，以「已连接设备 / DHCP 客户端 / 客户端列表」为准）。

| 品牌 | 登录地址 | 设备列表位置 |
|---|---|---|
| 水星 MERCURY / Mercusys | `melogin.cn` 或路由器 LAN IP | 已连接设备 / DHCP 服务器-客户端列表 |
| TP-Link | `tplinkwifi.net` 或 `192.168.1.1` | 已连接设备 / DHCP 客户端列表 |
| 小米 / Redmi | `miwifi.com` 或 `192.168.31.1` | 终端设备 / 连接设备 |
| 华为 / 荣耀 | `192.168.3.1`（部分 `192.168.8.1`） | 终端管理 / 已连接设备 |
| 华硕 ASUS | `router.asus.com` | 网络地图 / 客户端列表 |
| 电信天翼网关 | `192.168.1.1` | 已连接设备 / LAN 侧信息（机身铭牌多标 TEWA 系列型号） |

**核对时的两类差异**：
- 路由器有、扫描没有 → 设备休眠或用了静态地址，属正常漏报；
- 扫描有、路由器没有 → 该设备可能在上级网关之下（双层 NAT），或使用了静态地址。

**「IP与MAC绑定」≠「保留 IP」**：部分家用路由器（多见于入门型号）的这个页面只写静态 ARP（防 ARP 欺骗 / 便于管理），**未提供 DHCP 保留**——把本机 MAC 绑到某个地址后，设备仍可能沿用 DHCP 分到的地址，而绑定地址成了路由器代答的幽灵条目（详见 §一「判据的时效性」）。**不同型号、不同固件行为不一致，不要外推**；换机型请按同一办法自验：用**当前** MAC 绑一个别的 IP，再让该机断开重连，看它是否换到绑定地址。要真正固定 IP，通常只有两条路——客户端手工配静态地址（代价：换 Wi-Fi 网络要改回来），或固件另有「静态地址分配 / 地址保留」页。

**家长控制 / 上网限时也在这一层**：水星、TP-Link 一般在「上网控制 → 家长控制」，**按 MAC 匹配**。**先确认是白名单还是黑名单模式**——白名单模式下「掉出名单」= 到点断网；黑名单模式下「掉出名单」= 反而恢复上网，结论完全相反。确认模式后，再核对名单里的 MAC 是不是设备**当前**的 MAC。

**注意**：部分路由器后台的登录态为内存态令牌，无法用浏览器自动化接管。遇到这种情况，请用户在自己已登录的浏览器中查看设备列表并抄录主机名，不要索取密码。

## 七、隐私与合规

- MAC 地址、主机名、设备清单均属个人信息，**设备清单与主机名全程本地处理**，不上传、不外发。
- 查询厂商时只发送**单个 MAC 地址本身**（不发送设备清单、主机名或其他数据），且仅在用户允许在线查询时才发；本地 OUI 库匹配全程不联网。
- 只对本人拥有或管理的网络执行扫描。
- 报告文件写入用户指定的工作目录，不含凭据与口令。
